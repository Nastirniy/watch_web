## Routes and API versions

- Every path lives in `app/backend/enums/routes.py` as a plain `str` Enum (no `"/api/v1/..."` or `"/"` literal anywhere, tests included). New route: add the member to its group first, then `@router.get(XRoutes.MEMBER.value)`. A collection root is the group's own `ROOT = "/"`. `SystemRoutes` values are full paths; `DocsRoutes` are relative to a version (each version serves its own document); the other groups are relative to their `BASE`.
- Layout: `app/backend/api/vN/` holds the handler modules of version N (the folder is the version) and its contract: `api/vN/models/request/<resource>.py`, `.../response/<resource>.py`, `.../query/<resource>.py`, one file per route module (a model several modules use lives with its resource; response builders such as `post_to_response` sit next to their model). `api/shared/` holds version-neutral helpers only (no pydantic model there), `api/system/` health (its models in `health_checks.py`) and the problem pages. A module declares its place: `router = APIRouter(prefix=XRoutes.BASE.value, tags=[XRoutes.tag()])`.
- `api/vN/__init__.py` declares what the version publishes: `V1 = PublishedVersion(APIVersionRoutes.V1, auth, users, ...)` (`api/versioning.py`); a new module goes into that list. `main.py` includes `health.router`, `V1.router`, `problems.router`.
- A full path comes from the version: `V1.path(PostRoutes.POST_BY_ID, post_id=7)` (template without params, `LookupError` if the version does not publish it). A route that returns URLs takes `version: PublishedVersion = Depends(request_version)` and uses `version.path(...)`; never import `V1` inside a handler module.
- Versions run in parallel and never override each other: a version publishes only its own folder, `api/vN` never imports `api/vM`, no shared routers, no re-publishing. What two versions share lives in `services/` or `api/shared/`. A new version starts with only the resources whose contract changes; the client moves to it resource by resource while v1 keeps serving everything. Then: `include_router(V2.router)`, later `include_router(V1.router, deprecated=True)`, retire = remove the include and the folder. `tests/test_parallel_versions.py` is the working example (a second version next to v1: own module, its own `TagResponse`, a document, URLs and route-access per version).
- Each version has its own OpenAPI document and viewers (`/api/v1/openapi.json`, `/api/v1/docs`, `/api/v1/redoc`; nothing at the root): `PublishedVersion` serves them the way `FastAPI.setup()` does for an app, `V1.openapi(app)` is FastAPI's `get_openapi()` over the routes of the version plus the unversioned ones (`/health`). A component name and an operationId are unique within their version only: a v2 model may keep the name of a v1 model with other fields. A model v2 does not change is copied into `api/v2/models` under the same name, never imported from v1. No component name may carry a module path (`__`, `tests/test_openapi.py`).
- Shared by every version and kept outside the version folders: model base classes and validators (`utils/validators.py`), error codes and `/problems` (one catalog), domain enums (`enums/general.py`, `SortOrder` included). A version that needs another set of values declares its own enum with another name in its models; never change a domain enum for one version.
- Services, filters, models and workers never import `app.backend.api` (only `app/main.py` and `api_contract.py` do; test). A service returns dataclasses and the route converts: `XResponse.model_validate(result, from_attributes=True)`. A filter service declares what it filters by as a frozen dataclass next to itself (`TagCriteria(ListCriteria)`, `ObservationReportCriteria`) with its `SORTABLE_FIELDS`; the query model of a version (`Annotated[TagFilterParams, Query()]`, `api/v1/models/query/tags.py`, with the sort `Literal`, descriptions and limits) is converted in one place, `SimpleFilterEngine.criteria()` / `as_criteria()`: same field names, an unknown field is a `TypeError`. A new query field goes into both (`tests/test_filter_criteria.py`); a version whose names differ builds the criteria itself.
- Within one version, deprecate with what FastAPI already has: a new route next to the old one and `deprecated=True` on the old decorator (or `Query(deprecated=True)`); openapi-typescript marks it `@deprecated`.
- `tests/test_route_registry.py` fails on an enum member without a route, a route without an enum member, a route shadowed by an earlier one (register literal paths like `/list-all` before `/{id}`), an import between version folders, `api/shared` or `api/system` importing a version, a pydantic model in `api/shared` and a module outside `api/` importing it.

## Authorization

- Authentication and authorization live in `app/backend/auth/` (the request chain is in its `__init__` docstring): `require.py` (`require()`), `dependencies.py` (token, account, session, certificate), `context.py` (`AuthContext`), `service.py` (`AuthService`), `sessions.py`, `presence.py`, `access_control.py`, `access_errors.py`, `route_access.py`, `certificates.py`. Never put these back in `services/`.
- Every API route declares its requirement with a dependency, never a decorator:
  `auth: AuthContext = Depends(require(all=[Permissions.TAG_VIEW, Permissions.TAG_UPDATE], admin=True))`
  Use `require()` with no arguments for routes that only need an authenticated user. `auth.user` is the User row.
- `admin.true` is a GATE for administration routes (`admin=True`). It never substitutes a granular permission.
- Write routes require `X.view` AND `X.create` / `X.update` / `X.archive` (`role.delete` only for the permanent delete of roles).
- Data scope: `post.access_all` sees every post; otherwise the home post (`users.post_id`) plus `user_post_access` rows.
  Use `AccessControlService.resolve_post_scope(auth, filters.post_id)` for lists and `check_post_view` / `check_post_write` for single resources.
  Exception for post and user records only (not post data): administrators (`admin.true` plus the route's `X.view`) are not limited by post. Use `post_record_scope` / `check_post_record_view` for posts, `resolve_record_scope` and `check_user_visibility` for users. Aggregates and cross-user lists follow the same split: `GET /statistics` and `GET /media/uploads` with `media.manage_any` cover every post for administrators and `post_scope(auth)` for everyone else. Observations, media and reports never get this exception.
  Ownership overrides: `observation.manage_any`, `media.manage_any`.
- Raise 403 only through `access_denied(AccessErrorCode.X, required=..., missing=..., **params)` from `app/backend/auth/access_errors.py`.
- New permission: add it to `Permissions` in `app/backend/enums/general.py`, add its Ukrainian display name to `PERMISSION_META` in `app/backend/bootstrap/permissions.py`. Seeding grants it to the admin role automatically.
- Every route with `require()` appears in `GET /auth/route-access`; the test `tests/test_route_access.py` fails if a route under `/api/v1` has no requirement.
- Run tests with `venv\Scripts\python -m pytest` (in-memory sqlite, no MySQL needed).
- Add an entry to `CHANGELOG.md` for every change that affects the API or the database.
- Login sessions (`auth/sessions.py`) live while used: every request (`get_current_user`, at most once per touch interval) and every refresh calls `touch`, which moves `expires_at` to now + `security.session_idle_timeout_minutes`; `security.session_max_hours` (0 by default) is an optional hard limit since login. The state (`online` / `idle` / `ended`, `SessionStatus`) is computed when a row is read (`session_state`, SQL `live_clause()`), never stored; correctness never depends on a cleanup job, `record_end` only writes down an end the computation found. `end_reason` (`SessionEndReason`: logout, expired, idle_timeout, revoked) describes the session; why the server revoked it is `revoke_cause` (`SessionRevokeCause`), the account may be unchanged. Revoke through `AuthService.invalidate_all_user_sessions(cause=...)` in the transaction of the change that causes it. A production login binds the session to the client certificate (`certificate_fingerprint_hash`, RFC 8705 style): `certificate_matches` runs on every request and refresh (`token_certificate_mismatch`). Tokens come from `AuthService.session_tokens` (renewed at every refresh, never past the hard limit). There is no `user_sessions.is_active` (015).
- Presence: `User.last_activity_at` and `Post.online_user_count` / `Post.user_count` / `Post.last_user_activity_at` are column properties attached in `app/backend/models/presence_properties.py`; `User.is_online` is a Python property. A post has no stored connection status: it has users online when `online_user_count > 0` (filter `has_online_users`). Thresholds live in `settings.security` (`online_threshold_seconds`, `activity_touch_interval_seconds`); sessions are touched by `get_current_user`, no daemon. Post responses go through `post_to_response` in `api/v1/models/response/posts.py`.
- `include_deleted` on any list or search must be guarded with `AccessControlService.check_include_deleted(auth, params, Permissions.X_ARCHIVE)`.
- Archiving is the rule for every entity (roles, observations, users, media, dictionaries): `POST /{entity}/{id}/archive` sets `is_deleted=true`, `POST /{entity}/{id}/restore` clears it, both need `X.view` AND `X.archive`. Archived rows answer 404 on update and 409 on restore-when-not-archived. `is_deleted` is never accepted in a request body. Archived roles stop applying immediately (`load_auth_context` filters `Role.is_deleted`), archived tags stay attached to observations, archived media stays linked to its observation but is left out of `media_ids`.
- The only hard delete in the API is `DELETE /roles/{id}` (`role.view` + `role.delete`, administration). It removes an archived role with no active users, plus its `role_permissions` and `user_roles` rows, with core `delete()` statements (no ORM cascade in the async session). Never add another hard delete without a distinct permission, an archive-first precondition and a full copy of the removed rows in the audit log. Audit actions: `archive`, `restore`, `delete` (permanent only). An audit row is `create_audit_log(session, ..., **client_info(request, auth))`: the row from `services/audit.py`, who asked from `api/shared/helpers/audit_helper.py`.
- Renaming a permission needs a migration that renames the `permissions` row in place (see `010_archive_permissions`); seeding only inserts missing rows and refreshes `display_name` / `description` from `PERMISSION_META`.

## Errors (RFC 9457) and OpenAPI

- The error machinery lives in `app/backend/errors/`: `coded.py` (`CodedError`, `invalid()`, param checks; no FastAPI), `problems.py` (`ApiError`, `field_problem`, problem bodies), `handlers.py`, `openapi.py` (`problems()`). Services, filters, models, workers, enums, `bootstrap/` and `utils/` never reach FastAPI or Starlette, not even through another module (`tests/test_route_registry.py`): they raise `CodedError` and the route answers `ApiError.from_coded(exc)`.
- Every error is an RFC 9457 problem, `Content-Type: application/problem+json`: `type` (URI `<base>/problems/<code>`, `settings.app.problem_base_url` or the request origin), `title` (fixed per type), `status`, `detail` (title with params filled in), `instance` (request path), `code`, plus the params as extension members. FastAPI's own errors are wrapped by `app/backend/errors/handlers.py`: 422 is `validation_error` with `errors: [{code, detail, pointer | parameter + location, **params}]` (never the submitted input), unknown route / method / unparsable body have codes, any other framework status is `about:blank`, unhandled exceptions are 500 `internal_error` with an `error_id` logged once (`UnhandledErrorMiddleware`, outermost but for `RequestIdMiddleware`; never `add_exception_handler(Exception)`: Starlette re-raises after it and the server logs the error again, without the id), a 401 always has `WWW-Authenticate`.
- API or infrastructure: every error the API makes is a problem (the test client checks every error answer, `tests/helpers.py` `errors_are_problems`); what nginx answers on its own (client certificate, body size, API not reachable, file serving) is the infrastructure's, in nginx's format, and the client handles it by status (API.md, "Errors"). Never write problem bodies in nginx. Where nginx and the API check the same thing the API decides: nginx limits sit above the API's (`client_max_body_size` above `max_chunk_bytes` / `max_file_size_gb`, `tests/test_nginx_conf.py`), and the API checks that a file exists before `X-Accel-Redirect`.
- Request id: `RequestIdMiddleware` (`request_id.py`, the outermost middleware) keeps nginx's `X-Request-ID` (`$request_id`, 32 hex) or makes one; every response carries it, every log line has it (`{extra[request_id]}`, a loguru patcher), and the `error_id` of a 500 is the request id. nginx sets it in `nginx-proxy.conf`, answers it on every response (`add_header X-Request-ID $request_id always`, repeated in every location with add_header of its own) and logs it (`log_format watch_web`).
- A code is the key of exactly ONE message in the web localization package, never a category; a new message is a new code. Problem types live in `enums/errors.py` (`ErrorCode`, `AuthErrorCode`, `AccessErrorCode`) with their status, title, detail template and typed params (`problem(status, title, detail, **params)`); an `Optional[...]` param may be left out and is then absent from the body, never null. Field error codes (items of `validation_error`) are `FieldErrorCode`.
- Raise with `ApiError(ErrorCode.X, headers=..., **params)` (the status comes from the type); `access_denied(AccessErrorCode.X, required=..., missing=..., **params)` for 403; `invalid(FieldErrorCode.X, **params)` in request model validators; `field_problem(FieldErrorCode.X, ("body", "field"))` when a route checks a single value itself. Services raise `CodedError(ErrorCode.X, **params)` and the route converts it with `ApiError.from_coded(exc, headers=..., **extra)`. Never `HTTPException(detail=...)`, a hand-made error `JSONResponse` or a plain `ValueError` in a validator. Param names: at least 3 characters, never `type`, `title`, `status`, `detail`, `instance`, `code` (rename: `session_status`, `time_zone`).
- Never put exception text, file paths, SQL, stored internal reasons or the submitted `input` into a detail or a param; log them instead. Every loguru sink has `diagnose=False`: a traceback in the log never shows variable values (request bodies, tokens).
- Never turn `except Exception` into an error code, a `None` / `False` result or a log line: catch only the failure the code is about (`ClientDisconnect`, `OSError`, `ValueError` from a parser, `IntegrityError` of a known constraint) and let everything else reach the global 500 `internal_error` (logged with its `error_id`). Cleanup that must run on any failure catches, cleans up and re-raises. Allowed broad catches: worker loops, the health report, best-effort probes that document it.
- Every route declares the problems it answers on its decorator: `responses=problems(ErrorCode.POST_NOT_FOUND, ErrorCode.POST_CODE_TAKEN, *ADMIN)` (`app/backend/errors/openapi.py`; `*GUARDED` / `*ADMIN` are the 403 of `require(all=...)` / `require(..., admin=True)`). Generic ones are declared once and merged by FastAPI: `internal_error` on the app, the 401 set (`AUTHENTICATED`) and `validation_error` on the version router; login and refresh declare their own 401 set. With success helpers: `responses={**file_response(...), **problems(...)}`. A new `raise ApiError(Code.X)` needs `Code.X` in the route's `problems(...)`: the session fixture in `tests/conftest.py` fails on any problem the tests make the app answer that its operation does not declare. `openapi_document()` (FastAPI's `get_openapi` per version) only moves error content to `application/problem+json` and adds the schemas of framework problems; `/problems` and `/problems/{code}` (`api/system/problems.py`) read the document of every version. operationId = endpoint function name (unique within its version).
- A success response that is not a JSON model (file, image, empty body, headers) is declared with `responses=` from `api/shared/openapi_docs.py` (`file_response`, `empty_response`, `with_headers`; header sets of a version, such as `ORIGINAL_FILE_HEADERS`, live in its response modules); a JSON response always has a `response_model`.
- Client contract for the web team: `API.md` (errors, localization keys, openapi-typescript) and `WEB_TOOLING.md` (stock tools only: `openapi.json` -> openapi-typescript -> `tsc`, translations typed with `satisfies Messages`; starter files in `api-contract/web-kit/`). Never add a catalog, export format or checker of our own: whatever the web client needs must be in the OpenAPI document FastAPI generates.
- The contract is one file per version, `api-contract/v1/openapi.json` (the document `GET /api/v1/openapi.json` serves), committed. `tests/test_api_contract.py` fails on any difference and names the changed operations and schemas. Never rewrite it (`python -m app.backend.api_contract`) just to silence the test: first decide whether the change is intended (a renamed code or param breaks the web translations and types; a code gone from an operation means it was dropped from a `problems(...)` declaration). If intended: rewrite, commit the file with the change, add a CHANGELOG entry.
- `tests/test_error_contract.py` checks the catalog against RFC 9457, forbids hand-made error bodies and plain `ValueError` in validators, and checks every raise passes exactly the declared params; `tests/test_openapi.py` checks the generated document (problem+json errors, 401/403 follow `require()`, no JSON response without a schema, real bodies validate against their problem schema).

## Observation counters

- Observations are counted by `created_at`, never `observed_at` (`GET /posts/{id}/observation-stats`, `GET /statistics`). Counting lives in `services/observation_counts.py`; `observation-stats` is the only source of per-post counters, post responses carry none.
- Counters are aggregates: administrators (`admin.true`) count any post (`check_post_record_view`), everyone else their data scope. Figures are `not_archived` / `archived` pairs that never overlap; archived ones only on the explicit `include_archived` flag. It needs only `observation.view` (counts, not archived rows), so it is the one exception to the `check_include_deleted` rule.

## Observation frequencies

- Bands are rows of `observation_frequencies` (`ObservationFrequency`): `kind` from `FrequencyKind` in `enums/general.py` (no DB CHECK on it, a new kind is a new enum value), optional `link_group` for bands of one emitter, `bandwidth` generated by the database (never write it). An observation keeps at least one active band of any kind.
- Never query `observation_frequencies` directly: go through `filters/observation_frequency_filter.py` (`rows_query` joins observations for `is_deleted` of both tables and the post scope; `observation_has_band` puts every band condition in one subquery so they match the same band).
- Bands change only through `/observations/{id}/frequencies...` with `get_observation_for_write(lock=True)` from `api/shared/helpers/observation_helper.py`; removal is archive, never delete.

### Migration rule after 002_sync_schema

`002_sync_schema` creates every table from the models that is missing in the database. A later revision that creates a new table must either list the table in `TABLES_OWNED_BY_LATER_REVISIONS` inside `002_sync_schema_with_models.py` or guard its `create_table` with an inspector check, otherwise fresh installs fail with "table already exists". The same applies to columns and indexes: guard `add_column` / `create_index` with an inspector check (see `004_role_soft_delete_and_unique_assignments.py`).

## Media pipeline

- The API never decodes images or video. Thumbnails and previews are rendered on demand by imgproxy (libvips) from the original, or from the video poster, and cached by nginx. Only sign URLs in the API (`services/media/urls.py`, `services/media/imgproxy.py`).
- The only precomputed derived files are one poster JPEG per video at `<upload_path>/_derived/posters/{id // 1000:03d}/{id}.jpg` and, for videos of at least `storyboard.min_duration_seconds`, a storyboard (sprite sheets `<upload_path>/_derived/storyboards/{id // 1000:03d}/{id}/sheet-NNN.jpg`; the WebVTT is built per request), both extracted by `python -m app.backend.workers.media_worker` with ffmpeg. Job state is the `poster_*` columns on `media_files`; claim with the conditional UPDATE in `services/media/jobs.py` (no SKIP LOCKED, must keep working on sqlite tests). `enqueue_poster()` is called inside the upload transaction.
- Storyboards (seek previews): state is the table `video_storyboards` (model `VideoStoryboard`), claims and reconciliation live in `services/media/storyboard_jobs.py` (same conditional-UPDATE style as posters), never in `media_files` columns. A storyboard never delays a poster: the worker claims a poster first and a storyboard only when no poster was claimed and fewer than `storyboard.slots` run; `slots` must stay below `poster.concurrency` (the worker refuses to start otherwise). A completed poster enqueues the storyboard; stop cancels a running storyboard and gives the attempt back; output is written to a `.tmp-` directory and renamed, and the worker start removes leftover `.tmp-` / `.old-` directories older than `timeout_seconds`. `GET /media/{id}/storyboard` returns a WebVTT whose cues point at signed `/media-images/` URLs of the sheets (202 + Retry-After while pending, 409 `storyboard_failed`, 422 `storyboard_unsupported`); the API never decodes video for it. `MediaFileInfo.storyboard_status` is derived (`client_status`).
- `MediaFile.thumbnail_status` (ready, pending, processing, failed, unsupported) and `thumbnail_urls` are derived; never store thumbnail paths again. Never hand out a URL imgproxy will always refuse: an image above `storage.imgproxy.max_src_resolution_mp` (imgproxy's `IMGPROXY_MAX_SRC_RESOLUTION`, one compose variable for both, `tests/test_media_settings.py`) is `unsupported` (`too_large_to_render`, size read from the header at upload), and a video upload whose probe found only audio gets `poster_status = unsupported` (`jobs.mark_poster_unsupported`, at upload and in the worker; never claimed, no retries).
- `GET /media/{id}/thumbnail` must not have side effects. 202 + Retry-After while a poster is pending, 409 failed, 422 unsupported with the reason as its code (`thumbnails_unsupported`, `image_too_large_for_thumbnails`, `no_video_stream`).
- Public thumbnail URLs carry an `exp:` aligned to a ttl window (`quantised_expiry`) so nginx cache keys stay stable inside the window. Keep that property when touching URL building. Only imgproxy checks `exp:`, on a cache miss, and it caps the max-age of its answer at `exp:`: the `/media-images/` cache follows that header (never ignore `Cache-Control` there, no fixed `proxy_cache_valid` for 200, no stale copies), or an expired link keeps answering from the cache (`tests/test_nginx_conf.py`).
- Serve originals with `original_file_response` (X-Accel-Redirect behind nginx, FileResponse otherwise). Never read a whole file into memory in a route.
- Accepted upload formats are rows of `media_formats` (model `MediaFormat`), managed through `/media-formats` (permissions `media_format.*`, administration) and read through `services/media/formats.py` (`load_registry`, cached 15 s, `invalidate_registry_cache()` after every write). `DEFAULT_FORMATS` there only seeds missing rows; never hard-code a format in a route. Uploads answer 415 (format, with `Accept-Post`) or 413 (size, per-format `max_file_size_bytes`, capped by `storage.max_file_size_gb`). Keep defaults limited to what imgproxy renders, ffmpeg decodes and browsers play.
- Video and audio metadata (`duration_seconds`, `video_codec`, `audio_codec`, `playback_type`, `width`, `height`) come from `services/media/probe.py` (ffprobe, ffmpeg banner fallback): at upload in `record_upload` (`api/shared/helpers/upload_helper.py`), in the worker when missing, and via `media_tools probe-missing` (`--all` probes every row again). `playback_type` is the RFC 6381 string for `canPlayType`; never guess codecs from the MIME type. `width` and `height` are the size as displayed: the display rotation of a video and the EXIF orientation of an image (`image_dimensions`, header only) swap them.
- Resumable uploads (`api/v1/media_uploads.py`, `services/media/uploads.py`, table `upload_sessions`): progress is `received_bytes`, one writer per session via `writer_token`, chunks must arrive at `received_bytes` exactly, a failed chunk truncates the part file back. Completion goes through `store_file_from_path` like every other upload; never add a second storage path. Client contract in `UPLOADS.md`; keep it in sync with the status codes.
- Media maintenance commands: `python -m app.backend.media_tools {cleanup-legacy-thumbnails,reconcile-posters,poster-status,reconcile-storyboards,storyboard-status,probe-missing}`.
- Formats are checked live by `tests/docker/formats.py` against the e2e stack (every accepted image and video format plus edge cases through nginx); run it after a change to the probe, the worker, imgproxy or nginx settings.
- Deployment topology (`DEPLOYMENT.md`): Docker runs only api, media-worker and imgproxy on the host network. MySQL, the entry nginx and the media directory (local disk or a mounted network share) stay on the host; the media directory is bind-mounted at the same absolute path into every container. Do not add nginx or a database to docker-compose.yml.
- nginx is the control point for client certificates (`nginx.conf`: 443 with `ssl_verify_client on`, `ssl_client_certificate`, `ssl_crl`; 80 only redirects). Locations live in `nginx-app.conf` (shared with the e2e stack), the API proxy headers in `nginx-proxy.conf`. `POST /auth/login` trusts `X-SSL-Client-*` only because nginx sets them there: every location with `proxy_pass http://watch_web_api` includes that snippet (`tests/test_nginx_conf.py`). Login matches a serial in nginx's form (`0A1B`) and the stored one (`a1b`), `serial_hashes()` in `auth/certificates.py`. `nginx-app.conf` claims only the paths the API publishes (`tests/test_nginx_conf.py` checks every route); `/` is the web client, configured in `nginx.conf`. The API has no CORS: the web client is same origin (dev: the dev server's proxy, WEB_TOOLING.md section 8); a browser client on another origin gets CORS at nginx, never in the app.
